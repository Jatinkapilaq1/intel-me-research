SECTION 6: FIRMWARE UPDATE STRUCTURE
================================================================================

Intel ME firmware updates are delivered as encrypted packages.
The UPDATE PROCESS reveals code structure.

  ME firmware update flow:
    1. Lenovo downloads ME update from Intel (encrypted .bin)
    2. BIOS vendor (Insyde) embeds it in BIOS update
    3. BIOS update flashes ME region via SPI
    4. ME verifies the update using Intel's signing key
    5. ME decrypts and installs the update

  What this reveals:
    - ME has a self-update mechanism (fwupdate module)
    - Updates are signed by Intel (cannot be modified)
    - ME decrypts updates using its hardware key
    - The update format is standard ME firmware image

  We can analyze the update structure:
    - FPT (Flash Partition Table) header at offset 0x000000
    - Each partition has a 16-byte header
    - Module entries have 12-byte names + offset/size/metadata
    - The structure is the SAME in encrypted and unencrypted regions

SECTION 8: SIDE-CHANNEL ATTACK POTENTIAL
================================================================================

Side-channel attacks observe physical properties during execution:
  - Power consumption (DPA - Differential Power Analysis)
  - Electromagnetic emissions (TEMPEST)
  - Timing (cache-timing attacks)
  - Sound (acoustic cryptanalysis)

  Side-channel attack feasibility:

  Power Analysis (DPA):
    - Requires: Oscilloscope ($500+), current probe ($200+)
    - Difficulty: HIGH — ME uses constant-time crypto
    - Time: Weeks of data collection
    - Success probability: LOW

  Electromagnetic (TEMPEST):
    - Requires: Near-field probe ($1000+), spectrum analyzer ($5000+)
    - Difficulty: VERY HIGH — ME has EM shielding
    - Time: Months
    - Success probability: VERY LOW

  Timing Attacks:
    - Requires: High-precision timer, cache access
    - Difficulty: MEDIUM — but ME doesn't share cache with CPU
    - Success probability: LOW

  VERDICT: Side-channel attacks are theoretically possible
  but practically infeasible for independent researchers.

================================================================================
SECTION 9: FAULT INJECTION ATTACKS
================================================================================

Fault injection (glitching) causes errors in hardware execution:
  - Voltage glitching: Momentary voltage drop during execution
  - Clock glitching: Skipping clock cycles
  - Laser fault injection: Precise laser strikes on chip
  - EM fault injection: Electromagnetic pulses

  Fault injection feasibility:

  Voltage Glitching:
    - Requires: $50 glitching hardware (ChipWhisperer)
    - Target: ME's encryption verification check
    - Idea: Glitch the check to skip verification
    - Problem: ME uses redundant checks, hard to bypass
    - Success probability: LOW

  Clock Glitching:
    - Requires: Clock generator + FPGA
    - Target: ME's boot sequence
    - Idea: Skip the encryption initialization step
    - Problem: ME's boot is designed to detect glitches
    - Success probability: VERY LOW

  Laser Fault Injection:
    - Requires: $100,000+ equipment, cleanroom
    - Target: Individual transistors in PCH die
    - Idea: Disable encryption hardware directly
    - Problem: Physically destructive, may destroy chip
    - Success probability: LOW (and you lose the chip)

  VERDICT: Fault injection is the most promising hardware attack
  but requires significant investment and expertise.

THE BOTTOM LINE
================================================================================

The encrypted firmware IS accessible — but not through software.

The path Intel engineers use:
  1. They write code in C/ARC assembly
  2. They compile it with Intel's proprietary toolchain
  3. They encrypt it with Intel's hardware key
  4. They sign it with Intel's signing key
  5. They distribute it to BIOS vendors
  6. BIOS vendors embed it in BIOS updates
  7. ME decrypts it at boot using hardware fuses

To reverse this process, you'd need:
  - Access to Intel's encryption key (hardware fuses)
  - OR ability to intercept decrypted code at runtime
  - OR ability to bypass the encryption check

The most realistic path for us:
  1. Fuzz the HECI interface (no cost)
  2. Reverse-engineer MEIx64.sys (no cost)
  3. Monitor ME network traffic (no cost)
  4. Use Intel PT to trace ME execution (no cost)
  5. Build a CH341A programmer for direct flash access ($5)

These approaches won't give us the decrypted code, but they WILL
give us a deeper understanding of ME's behavior and capabilities.

THE ENCRYPTION IS A BARRIER, NOT A WALL.
We can still learn a LOT from the outside.
